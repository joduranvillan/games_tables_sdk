Proc-macros derive para juegos construidos sobre OpenTable SDK.

Sin esto, cada Command/Event/Resource/Component de un juego necesita escribir a mano as_any(), #[derive(bevy_ecs::system::Resource)], o el impl bevy_ecs::component::Component con su Storage asociado. Estos cuatro derives generan exactamente ese boilerplate mecánico, nada más - la lógica de juego (validaciones, reglas) sigue viviendo en el crate del juego, no acá.

Asume que el crate que los usa depende de open_table_core (siempre) y, para GameResource/GameComponent, también de bevy_ecs bajo esos nombres exactos.

Derive Macros§

GameCommand
#[derive(GameCommand)]: genera impl Command for T con as_any().
GameComponent
#[derive(GameComponent)]: implementa tanto open_table_core::Component como bevy_ecs::component::Component (con la estrategia de almacenamiento TableStorage por defecto).
GameEvent
#[derive(GameEvent)]: genera impl Event for T.
GameResource
#[derive(GameResource)]: implementa tanto open_table_core::Resource (el marcador del SDK) como bevy_ecs::resource::Resource (lo que Session/RuleEngine necesitan para poder insertarlo en el World).
