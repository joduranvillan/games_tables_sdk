pub fn process_command( &mut self, sender: PlayerId, command: Box<dyn Command>, ) -> EngineResult<Vec<Box<dyn Event>>>

Único punto de entrada para mutar el estado de la partida.

sender tiene que venir de Transport::poll_received() (la identidad ligada a la conexión de red real), nunca de un campo dentro de command. Si command.issuer() es Some y no coincide con sender, se rechaza sin ejecutar nada — esto es lo que impide que un cliente mande comandos en nombre de otro jugador.

§Examples
use open_table_engine::prelude::*;
let session = Session::new(SessionId(1), 42, vec![PlayerId(1), PlayerId(2)], RuleEngine::new());
assert_eq!(session.current_tick(), Tick(0));

pub fn world_mut(&mut self) -> &mut BevyWorld

Acceso mutable al World para el SETUP INICIAL de un juego (ej: insertar el Resource del tablero antes de la primera jugada). Esto no viola el invariante “solo process_command muta el World” en espíritu: está pensado para usarse una sola vez, antes de que la partida arranque, nunca durante el loop de juego. La lógica de una jugada real SIEMPRE tiene que pasar por una regla registrada en el RuleEngine, no por acá.

pub fn replay( id: SessionId, seed: u64, players: Vec<PlayerId>, rules: RuleEngine, log_bytes: &[u8], ) -> EngineResult<Session>

Reconstruye una Session desde cero reproduciendo un log exportado con export_log. Usa command.issuer() como sender en cada paso (el log solo contiene comandos que ya pasaron la validación de identidad la primera vez, así que esto es seguro).

pub fn replay_collecting_events( id: SessionId, seed: u64, players: Vec<PlayerId>, rules: RuleEngine, log_bytes: &[u8], ) -> EngineResult<(Session, Vec<Box<dyn Event>>)>

Igual que replay, pero además devuelve TODOS los eventos producidos durante la reproducción. Es la base del mecanismo de resync: en vez de serializar el World de bevy_ecs (genérico y difícil), reproducimos el log y le mandamos al cliente reconectado solo los eventos que su Visibility le permite ver — filtrando con filter_events_for_player.
