OpenTable SDK

OpenTable SDK v1.0.0 — Introduction

OpenTable SDK is a deterministic, cross-platform board-game engine and toolkit written in Rust (open_table_core, open_table_engine, open_table_godot) with a complete visual client in Godot 4 / Redot.

Key Capabilities

  • 13 Complete Deterministic Board Games: Chess, Checkers, Go, Shogi, Xiangqi, Backgammon, Ludo, Uno, Monopoly, Crisis, Mille Bornes, Chinese Checkers, and Battleship.
  • Deterministic ECS & Rule Engine: Seeded ChaCha8 RNG, cryptographic state hashing, full command/event replay, and hidden-information sanitization for cards/fog-of-war.
  • Parametric AI Suite: Minimax with Alpha-Beta pruning, ECO compact opening book (Chess), and Monte Carlo Tree Search (Go), configurable across Easy, Medium, Hard, and Expert.
  • Multiplayer & Competitive Stack: Local Hotseat, LAN TCP, Native P2P (Wi-Fi Direct / BLE), and WebSocket Relay with persistent SQLite ELO rankings (GET /rankings/:game_id) and single-elimination tournaments (4/8/16 players).
  • Godot 4 / Redot Addon (addons/open_table/): Drop-in GDExtension bridge (OpenTableBridge), interactive step-by-step tutorials (TutorialManager), themes, colorblind mode, and procedural audio.

OpenTable SDK — Guía de Integración Rápida en 15 Minutos (SDK_QUICKSTART.md)

Esta guía muestra cómo implementar tu propio juego de mesa determinista desde cero usando los traits de open_table_core, registrarlo en una sesión autoritativa de open_table_engine y conectarlo con las señales de Godot / Redot en menos de 15 minutos.

1. Arquitectura en 30 segundos

Cada juego en OpenTable SDK se define mediante tres elementos puros en Rust:

  1. State (Resource ECS): El estado del tablero y el turno actual (PlayerId).
  2. Action / Command (#[game_command]): La intención serializable enviada por un jugador.
  3. GameEngine / Regla de validación: Función pura que valida (&mut World, PlayerId, &dyn Command) y emite Box<dyn Event>.

2. Ejemplo completo: Tres en Línea (Tic-Tac-Toe) en < 100 líneas de Rust

#![allow(unused)]
fn main() {
use bevy_ecs::prelude::*;
use open_table_core::{Command, Event, GameError, PlayerId, RuleEngine};
use open_table_macros::{game_command, game_event};
use serde::{Deserialize, Serialize};

/// 1. Estado del juego (State) almacenado en el World ECS
#[derive(Resource, Debug, Clone, Serialize, Deserialize)]
pub struct TicTacToeState {
    pub grid: [[Option<PlayerId>; 3]; 3],
    pub current_turn: PlayerId,
    pub winner: Option<PlayerId>,
}

impl Default for TicTacToeState {
    fn default() -> Self {
        Self {
            grid: [[None; 3]; 3],
            current_turn: PlayerId(1),
            winner: None,
        }
    }
}

/// 2. Acción del jugador (Action / Command)
#[game_command]
pub struct PlaceMarkCommand {
    pub row: usize,
    pub col: usize,
}

/// 3. Evento resultante para notificar a la vista (Godot / Redot)
#[game_event]
pub struct MarkPlacedEvent {
    pub player: PlayerId,
    pub row: usize,
    pub col: usize,
    pub winner: Option<PlayerId>,
}

/// 4. Trait GameEngine para encapsular reglas y consulta de jugadas
pub trait GameEngine {
    type State;
    type Action;
    fn apply_action(state: &mut Self::State, player: PlayerId, action: &Self::Action) -> Result<Option<PlayerId>, GameError>;
}

pub struct TicTacToeEngine;

impl GameEngine for TicTacToeEngine {
    type State = TicTacToeState;
    type Action = PlaceMarkCommand;

    fn apply_action(state: &mut Self::State, player: PlayerId, action: &Self::Action) -> Result<Option<PlayerId>, GameError> {
        if state.winner.is_some() {
            return Err(GameError::InvalidAction("La partida ya terminó".into()));
        }
        if state.current_turn != player {
            return Err(GameError::NotYourTurn);
        }
        if action.row >= 3 || action.col >= 3 || state.grid[action.row][action.col].is_some() {
            return Err(GameError::InvalidMove("Casilla inválida u ocupada".into()));
        }
        state.grid[action.row][action.col] = Some(player);
        let lines = [
            [(0, 0), (0, 1), (0, 2)], [(1, 0), (1, 1), (1, 2)], [(2, 0), (2, 1), (2, 2)],
            [(0, 0), (1, 0), (2, 0)], [(0, 1), (1, 1), (2, 1)], [(0, 2), (1, 2), (2, 2)],
            [(0, 0), (1, 1), (2, 2)], [(0, 2), (1, 1), (2, 0)],
        ];
        if lines.iter().any(|l| l.iter().all(|&(r, c)| state.grid[r][c] == Some(player))) {
            state.winner = Some(player);
        } else {
            state.current_turn = if player == PlayerId(1) { PlayerId(2) } else { PlayerId(1) };
        }
        Ok(state.winner)
    }
}

/// 5. Registro en RuleEngine y open_table_engine::Session
pub fn register_tic_tac_toe(world: &mut World, rules: &mut RuleEngine) {
    world.insert_resource(TicTacToeState::default());
    rules.add_command_validator(|world, player, cmd| {
        let Some(action) = cmd.as_any().downcast_ref::<PlaceMarkCommand>() else {
            return Ok(vec![]);
        };
        let mut state = world.resource_mut::<TicTacToeState>();
        let winner = TicTacToeEngine::apply_action(&mut state, player, action)?;
        Ok(vec![Box::new(MarkPlacedEvent {
            player,
            row: action.row,
            col: action.col,
            winner,
        }) as Box<dyn Event>])
    });
}
}

3. Registro en open_table_engine::Session

Para crear una sesión local, contra IA o en red (TCP / WebSocket Relay) con historial de repetición (ActionHistory):

#![allow(unused)]
fn main() {
use bevy_ecs::world::World;
use open_table_core::{PlayerId, RuleEngine};
use open_table_engine::EngineSession;

fn start_session() -> EngineSession {
    let mut world = World::new();
    let mut rules = RuleEngine::new();
    register_tic_tac_toe(&mut world, &mut rules);
    EngineSession::new(world, rules)
}
}

4. Conexión con Godot / Redot vía Señales

En tu escena de Godot (res://scenes/tic_tac_toe_board.gd), instancia OpenTableBridge y conecta sus señales:

extends Node2D

var bridge: OpenTableBridge

func _ready() -> void:
    bridge = OpenTableBridge.new()
    add_child(bridge)
    bridge.board_updated.connect(_on_board_updated)
    bridge.game_over.connect(_on_game_over)
    bridge.move_rejected.connect(_on_move_rejected)

func enviar_jugada(player_id: int, fila: int, columna: int) -> void:
    var cmd := {
        "command_type": "PlaceMarkCommand",
        "row": fila,
        "col": columna
    }
    bridge.send_command_json(player_id, JSON.stringify(cmd))

func _on_board_updated(state_json: String) -> void:
    var state = JSON.parse_string(state_json)
    queue_redraw()

func _on_game_over(winner_id: int) -> void:
    print("¡Victoria del jugador %d!" % winner_id)

func _on_move_rejected(reason: String) -> void:
    print("Movimiento rechazado: ", reason)

Architecture Overview

OpenTable SDK follows a strict, unidirectional layered architecture where inner layers have zero knowledge of outer layers or rendering engines:

+-------------------------------------------------------------------------+
|                        Godot 4 / Redot Client                           |
|   Scenes (chess_board, go_board, leaderboard, tournament_lobby, ...)    |
|   Autoloads (GameManager, ThemeManager, AudioManager, TutorialManager)  |
+------------------------------------+------------------------------------+
                                     |
                           GDScript Signals & Calls
                                     v
+-------------------------------------------------------------------------+
|                    Bridge Layer (open_table_godot)                      |
|      GDExtension C-ABI FFI (`OpenTableBridge`) + JSON Serialization     |
+------------------------------------+------------------------------------+
                                     |
                      CommandEnvelope / EventEnvelope
                                     v
+-------------------------------------------------------------------------+
|          Game Modules (13 Crates: chess_game, go_game, ...)             |
|   Rules, Legal Move Generators, Parametric AI (Minimax / MCTS / Book)   |
+------------------------------------+------------------------------------+
                                     |
                     RuleRegistration & ECS Components
                                     v
+-------------------------------------------------------------------------+
|                  Engine Layer (open_table_engine)                       |
|    `bevy_ecs` World + Deterministic Scheduler + Replay + Snapshots      |
+------------------------------------+------------------------------------+
                                     |
                         Foundational Contracts
                                     v
+-------------------------------------------------------------------------+
|                   Core Layer (open_table_core)                          |
|   Traits (`Command`, `Event`, `Resource`, `Transport`), `AiDifficulty`  |
+-------------------------------------------------------------------------+

Layer Responsibilities

  1. open_table_core: Pure data contracts (Command, Event, Component, Resource, Transport, Visibility, AiDifficulty, GameResult) with no engine or I/O dependencies.
  2. open_table_engine: Authoritative EngineSession powered by bevy_ecs, deterministic RuleEngine, replay recording/verification, and spectator state filtering.
  3. Game Crates (*_game): Self-contained rules, state machines, and AI engines for each of the 13 supported board games.
  4. Transports & Relay (open_table_transport_*, open_table_relay): TCP, WebSocket, and Native P2P transports plus matchmaking, persistent SQLite ELO ratings, and tournament brackets.
  5. Godot Bridge (open_table_godot): Exposes OpenTableBridge to GDScript so UI boards remain thin, reactive views driven by engine events.

En la pestaña Salas Online:

  1. Revisa tu ELO actual para el juego seleccionado.
  2. Elige la Tolerancia ELO Inicial:
    • ±100 ELO (Estricto): Busca rivales de nivel muy cercano.
    • ±200 ELO (Estándar): Balance óptimo entre velocidad y equilibrio competitivo.
    • ±400 ELO (Amplio): Emparejamiento rápido.
  3. Pulsa Buscar Partida Online.
  4. Si no aparece un oponente en los primeros 10 segundos, la ventana se expande automáticamente (±100 → ±200 → ±400) y se sincroniza con open_table_relay.
  5. Si deseas jugar sin esperar a otro humano en línea, pulsa Jugar vs IA Calibrada Ahora para iniciar inmediatamente contra el nivel de IA que mejor se ajusta a tu ELO.

4. Organizador de Torneos y Ranking ELO FIDE ($K=32$)

A. Pestaña Torneos

  • Formatos Soportados:
    • Liga Round-Robin (Tablas de Berger): Todos contra todos. Otorga 1.0 punto por victoria, 0.5 por empate y 0.0 por derrota, ordenando la clasificación por puntos, coeficiente Sonneborn-Berger (SB) y victorias.
    • Eliminatoria Directa (Knockout): Cuadro eliminatorio con avance automático del ganador a la siguiente ronda hasta coronar al campeón.
  • Participantes Mixtos (2 a 8): Combina jugadores humanos y bots de IA de cualquier dificultad.
  • Integración con el Tablero: Pulsa Jugar en Tablero en cualquier enfrentamiento pendiente para disputarlo en vivo; al concluir la partida, el ganador se registra automáticamente en el cuadro del torneo.

B. Pestaña Ranking ELO

  • Calcula la variación de rating tras cada partida con la fórmula oficial FIDE ($K=32$): $$E_A = \frac{1}{1 + 10^{(R_B - R_A)/400}}, \quad \Delta R = \text{round}(32 \times (S - E_A))$$
  • Desbloquea automáticamente 7 logros competitivos (Primera Victoria, Racha Imparable, Conquistador Polivalente, Maestro Táctico 1300+, Gran Maestro 1500+, Vencedor de IA Maestra y Campeón de Torneo).
  • Permite Exportar / Importar tu perfil completo en JSON y Sincronizar tu ELO con la sala Relay activa.

5. Analizador Post-Partida y Visor de Repeticiones

A. Pestaña Analizador

Evalúa todas las jugadas de la partida actual (o de una partida de demostración/JSON importado) para cualquiera de los 14 juegos:

  • Gráfico SVG de Ventaja Posicional ($[-100, +100]$): Muestra la evolución de la ventaja turno a turno (valores positivos favorecen al Jugador 1; negativos al Jugador 2).
  • Clasificación Automática de Jugadas:
    • ★ Óptima: Ganancia neta $\ge +5$ puntos de ventaja.
    • ✓ Buena: Mantiene la ventaja (pérdida $\le 4$ puntos).
    • ? Imprecisión: Caída moderada de ventaja ($4 < \text{pérdida} < 15$).
    • ?? Error Crítico: Caída severa de ventaja ($\ge 15$ puntos).
  • Haz clic en cualquier punto de la gráfica o fila de la tabla y pulsa Cargar Estado de Este Turno en el Tablero Principal para explorar variantes desde esa posición.

B. Barra de Replay en el Tablero Principal

Situada encima del tablero activo, permite desplazarse a cualquier paso (|<<, <, slider, >, >>|), exportar el historial completo a .json o cargar una partida guardada.

2. Guía Paso a Paso: Cómo Crear o Extender Tableros SVG y Motores de Juego

A. Flujo Unidireccional de Datos en los Tableros React

Todos los tableros en web_client/src/components/boards/<Game>Board.tsx son componentes puros controlados por estado JSON. Ningún componente de tablero muta reglas localmente; todo cambio pasa por onDispatchCommand(cmdJson):

export interface StandardBoardProps {
  stateJson: string;
  legalMovesJson: string;
  isLocalTurnAllowed: boolean;
  localPlayerId: 1 | 2;
  onDispatchCommand: (cmdJson: string) => void;
}
  1. Lectura del Estado: El componente parsea JSON.parse(stateJson) y JSON.parse(legalMovesJson).
  2. Resaltado de Jugadas Legales: Cuando el usuario selecciona una pieza o casilla origen (r, c), el tablero filtra legalMoves para iluminar únicamente los destinos válidos (to_r, to_c).
  3. Bloqueo de Turno (isLocalTurnAllowed):
    • En modo spectator o cuando el visor de Replay está en un turno histórico (!isReplayAtLiveHead), isLocalTurnAllowed es false y el tablero bloquea cualquier disparo de comandos.
    • En modo online_relay, solo permite actuar cuando currentTurn === localPlayerId.
  4. Despacho del Comando: Al confirmar la acción, el tablero llama a: 
    onDispatchCommand(JSON.stringify({
  command_type: "MovePieceCommand",
  from: [fromRow, fromCol],
  to: [toRow, toCol],
}));

B. Checklist para Añadir o Extender un Juego

Si deseas extender un juego existente o incorporar una nueva variante:

  1. Motor Rust (<juego>_game y open_table_wasm/src/lib.rs):
    • Registra el constructor de sesión en create_session_for_players y el prefijo de comandos en parse_command_json dentro de open_table_wasm/src/lib.rs.
    • Añade la rama de IA en step_ai_if_needed.
  2. Puente Isomórfico (web_client/src/wasm_pkg/index.ts):
    • Asegúrate de que resetGameState, get_legal_moves_json, send_command_json y step_ai_if_needed manejen el game_type con el mismo contrato JSON.
  3. Componente de Tablero (web_client/src/components/boards/<Juego>Board.tsx):
    • Renderiza el tablero en SVG vectorial responsivo con etiquetas aria-label y soporte para el atributo global [data-okabe-ito="true"] si utiliza indicadores de color.
  4. Evaluador Posicional (PostMatchAnalyzerPanel.tsx):
    • Registra la función de evaluación normalizada ($[-100, +100]$) en evaluateBoardAdvantageForPlayer1(gameType, state).
  5. Autodiagnóstico y Tests (SystemDiagnosticsPanel.tsx y src/__tests__/):
    • Añade el juego a la matriz de regresión para que tanto el Panel de Diagnóstico en vivo como Vitest lo verifiquen en cada commit.

3. Protocolo WebSocket Relay, Matchmaking ELO y Sincronización

El módulo web_client/src/bridge/relayClient.ts (RelayWebSocketClient) implementa el protocolo completo del servidor Rust open_table_relay (open_table_relay/src/lib.rs y open_table_relay/src/room.rs).

A. Mensajes Cliente → Servidor (RelayRequest)

// 1. Crear sala privada de 6 caracteres (asigna player_id: 1)
{ "action": "create" }

// 2. Unirse como Jugador 2 a una sala existente
{ "action": "join", "code": "AB12CD" }

// 3. Unirse como Espectador en vivo (solo lectura, player_id: 0)
{ "action": "spectate", "code": "AB12CD" }

// 4. Entrar en Cola de Matchmaking Automático con filtro por Rango ELO (Fase 5)
{
  "action": "queue",
  "game_type": "chess",
  "elo": 1248,
  "max_elo_delta": 200
}

// 5. Retransmitir comando, snapshot SyncState, ELO o mensaje de chat a la sala
{
  "action": "relay",
  "payload": "{\"kind\":\"command\",\"playerId\":1,\"cmdJson\":\"{...}\"}"
}

B. Eventos Servidor → Cliente (RelayResponse)

  • {"event": "created", "code": "AB12CD", "player_id": 1}
  • {"event": "joined", "code": "AB12CD", "player_id": 2}
  • {"event": "spectating", "code": "AB12CD"}
  • {"event": "queued", "game_type": "chess"}
  • {"event": "matched", "code": "X9M2K1", "player_id": 2}
  • {"event": "peer_joined", "player_id": 2} (Dispara el envío automático de SyncState con export_log_json() desde el Host).
  • {"event": "relayed", "from": 1, "payload": "..."}

C. Sobres Internos en payload (RelayEnvelope)

Para mantener compatibilidad total con open_table_relay sin alterar el framing del servidor, RelayWebSocketClient encapsula dentro de payload cuatro tipos de sobre JSON:

  1. kind: "command": { kind: "command", playerId, cmdJson } — aplica el comando en el WasmGameBridge remoto.
  2. kind: "sync_state": { kind: "sync_state", gameType, logJson } — sincroniza a jugadores recién conectados o espectadores tardíos mediante apply_sync_log_json.
  3. kind: "chat": { kind: "chat", message: { id, senderName, senderRole, text, timestamp } } — alimenta el panel RelayChatPanel.
  4. kind: "elo_sync": { kind: "elo_sync", playerId, rating, playerName } — muestra el ELO del rival en la sala y lo usa para el cálculo K=32 al terminar la partida.

4. Pipeline de Compilación wasm-bindgen, Testing Vitest y Despliegue PWA

A. Compilación del Crate Rust open_table_wasm

El script games_tables_sdk/tools/build_wasm.sh (ejecutado también en .github/workflows/ci.yml, release.yml y docs.yml) compila los 14 motores de Rust a WebAssembly:

# 1. Compilar el binario .wasm en modo release
cargo build --manifest-path games_tables_sdk/open_table_wasm/Cargo.toml \
  --target wasm32-unknown-unknown --release

# 2. Generar bindings JS/TS para la web en web_client/public/wasm/
wasm-bindgen --target web \
  --out-dir games_tables_sdk/web_client/public/wasm \
  games_tables_sdk/open_table_wasm/target/wasm32-unknown-unknown/release/open_table_wasm.wasm

B. Suites de Pruebas Automatizadas en Vitest (web_client/src/__tests__/)

Ejecuta npm --prefix games_tables_sdk/web_client test para correr las 6 suites de verificación:

  1. boards_14_games.test.tsx: Verifica el renderizado SVG y el despacho de una jugada legal en cada uno de los 14 tableros React.
  2. network_turn_lock_and_persistence.test.ts: Verifica el bloqueo de turnos en red (computeIsLocalTurnAllowed), modo espectador y reconexión.
  3. phase3_features.test.ts: Verifica relojes de torneo FIDE/Byo-yomi, visor de repeticiones paso a paso y tutoriales interactivos.
  4. phase4_ecosystem.test.ts: Verifica el motor ELO FIDE ($K=32$), los 7 logros, los torneos Round-Robin Berger y Eliminatoria Directa, temas Okabe-Ito y chat Relay.
  5. phase5_matchmaking_and_analyzer.test.ts: Verifica la cola de Matchmaking por rango ELO y el Analizador Post-Partida ($[-100, +100]$) en los 14 juegos.
  6. self_diagnostics_and_docs.test.ts: Verifica el motor de autodiagnóstico en vivo (runFullSystemDiagnostics) sobre los 14 juegos y la integridad del centro de documentación.

C. Empaquetado PWA Offline y Despliegue en GitHub Pages

  • Service Worker y Manifiesto:
    • web_client/public/manifest.webmanifest define iconos, colores y modo standalone.
    • web_client/public/sw.js implementa caché Stale-While-Revalidate para precachear el shell HTML/JS/CSS y el binario .wasm, permitiendo jugar los 14 juegos 100% offline.
  • Despliegue Continuo (.github/workflows/docs.yml):
    • En cada push a main, GitHub Actions compila open_table_wasm, construye web_client/dist, compila el libro mdBook (docs/book) junto con cargo doc, y publica la PWA en la raíz (/) de gh-pages y la documentación técnica en /docs.
